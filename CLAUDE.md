# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Tostrr is an Android app (package `app.tostrr`) that tracks Tesla vehicle orders: it logs into the Tesla owner API, polls the (undocumented) order endpoints, shows order progress, records a change history, sends notifications, and offers home-screen widgets and a native delivery-day checklist. Kotlin, Jetpack Compose (Material 3), Glance widgets, WorkManager, Room, OkHttp, kotlinx.serialization. DI is Koin with Koin Annotations (KSP): classes are annotated `@Single` / `@Factory` (use cases) / `@KoinViewModel` / `@KoinWorker` and picked up by `@ComponentScan`: one Koin module per Gradle module, `DomainModule` (`app.tostrr.domain.di`) and `DataModule` (`app.tostrr.data.di`) included by `AppModule` in `:app`. Our own classes always carry the annotation themselves (take `Context` and derive paths inside rather than being built in a provider); the module classes only provide types we don't construct (`DataModule`: OkHttp, Room database/DAO, `WorkManager`; `AppModule`: the app `CoroutineScope`); `TostrrApp.onCreate()` calls `startKoin`. `KOIN_CONFIG_CHECK` (in `:data` and `:app`) makes a missing dependency fail the build; it runs per Gradle module and can't see across them, so it is off in `:domain` and the whole graph is checked by `KoinGraphTest` in `:app` (koin-test `verify()`), which fails if a domain interface has no implementation. Koin is pinned to 4.1.x because 4.2 needs Kotlin 2.3. WorkManager is initialised through Koin's `workManagerFactory()` (default initializer removed in the manifest); Glance widgets get dependencies as `KoinComponent`s.

The app ships English and French only (`androidResources.localeFilters` in `app/build.gradle.kts` drops the libraries' other translations): English is the default (`res/values/strings.xml`, also used on any device in another language), French is in `res/values-fr/strings.xml`; every new string goes in both. Code comments and identifiers are in English. Composables (screens, components, Glance widgets) never hold literal text: it lives in those string files, keys prefixed by screen (`orders_`, `detail_`, `checklist_`, `settings_`, `login_`, `update_`, `widget_`, `countdown_`; `common_` / `order_` for shared ones), read with `stringResource` / `pluralStringResource` (Glance: `LocalContext.current.getString`). A helper that picks a text returns its `@StringRes` id (`DetailBlock.titleRes`); one outside composition takes `Resources` (`countdownLabels`). No user-facing text is written in Kotlin anywhere. `:domain` has no resources, so it returns what to word instead of words: `StepKind`, `DeliveryMethod`, Tesla's payment codes (`PaymentInfo.status`, `financeProduct`, worded or `humanizeCode`d by the screen), `Alert` subtypes from `OrderAlerts` (worded by `OrderNotifier`), `AuthError` on `AuthException`, the HTTP code on `ApiException`, and checklist ids (`DeliveryChecklist` sections/questions `<section>-<nn>`, worded through `ui/checklist/components/ChecklistTexts.kt` and `checklist_strings.xml`). ViewModels expose failures as `ui/common/UiError`, worded by `uiErrorText`. `:data` has its own `res/values{,-fr}/strings.xml` for notifications and their channels. Values from Tesla (delivery window, appointment text) come in the language the API is asked for (`deviceLanguage`, the device's); dates follow the device's locale (`domain/order/LocalDateFormats`, `ui/common/Format.kt`; the domain tests run in `fr_FR`, set in `domain/build.gradle.kts`), amounts and numbers too (`OrderInfoMapper.formatMoney`: the currency Tesla gives, written the device's way).

## Commands

The system `java` here is a JRE without javac and Android Studio's JBR is too new for AGP 8.11, so set `JAVA_HOME` explicitly (shell is fish; wrap multi-line scripts in `bash -c`):

```bash
JAVA_HOME=/home/arnaud/.gradle/jdks/eclipse_adoptium-21-amd64-linux.2 ./gradlew :app:assembleDebug
```

- Unit tests: `./gradlew :domain:test :data:testDebugUnitTest :app:testDebugUnitTest` (`:app`: ViewModel tests, screen tests and the Koin graph check)
- Single test: `./gradlew :domain:test --tests 'app.tostrr.domain.alert.OrderAlertsTest'` (append `.methodName` for one method)
- Install: `ANDROID_SERIAL=<serial> ./gradlew :app:installDebug` — always set `ANDROID_SERIAL`, otherwise it installs on every connected device.
- Release: every push to `main` runs `.github/workflows/release.yml`, which publishes `versionName` (in `app/build.gradle.kts`) as the GitHub release `v<versionName>` once: if that release exists the version wasn't bumped and nothing is published. It runs the unit tests, then `:app:assembleRelease` signed with the keystore from the repository secrets (`TOSTRR_KEYSTORE_BASE64`, `TOSTRR_KEYSTORE_PASSWORD`, `TOSTRR_KEY_ALIAS`, `TOSTRR_KEY_PASSWORD`), with the workflow run number as versionCode and the Firebase config from the `TOSTRR_GOOGLE_SERVICES_JSON` secret; a versionName with a suffix (`1.2.0-beta.1`) is a pre-release. The release is created as a draft, with GitHub's generated notes to rewrite: publishing it by hand is what offers it to the installed apps (see **Updates**). `app/build.gradle.kts` reads the key from the `tostrrStoreFile` / `tostrrStorePassword` / `tostrrKeyAlias` / `tostrrKeyPassword` Gradle properties or a git-ignored `signing.properties` at the root; without it the release APK is unsigned. The keystore itself is never committed.

There is no lint/format config beyond `kotlin.code.style=official`. Tests are JUnit 4, all on the JVM (no instrumented tests: on a device they would run inside the real `app.tostrr` install and its session). `domain/src/test` covers the pure `:domain` module (rules, mapping, and the use cases over small fakes of the repository interfaces). `data/src/test` runs the real repositories under Robolectric (SDK 35, English resources): files, shared preferences and an in-memory Room database; no network, `testing/FakeHttp` is an `OkHttpClient` answering from canned bodies per URL path, and `testing/FakeAndroidKeyStore` stands in for the Android Keystore Robolectric lacks, so `TokenStore`, `TeslaAuth` and everything above them run for real. `app/src/test` has `KoinGraphTest`, a unit test per ViewModel (`MainDispatcherRule`, `watch(viewModel)` to subscribe to its state, `sideEffects(viewModel)`) and a Compose test per screen (`…ScreenTest`, Robolectric on SDK 35 with a bare `Application`, in French, see `app/src/test/resources/robolectric.properties`; `EnglishScreensTest` checks the English resources), which renders the real screen with its real ViewModel and use cases. Both build them through `testing/TestGraph` on the in-memory fakes of `testing/Fakes.kt` (one per repository interface; set their state, read what was called); a new ViewModel or use case gets its factory there, a new repository its fake.

`api/` contains only stale build output from removed modules; it is not part of the Gradle build.

## Architecture

**Modules / layers**: `:domain` (Kotlin JVM library, no Android: JSON → model, rules; this is what's unit-tested) ← `:data` (Android library: network, auth, persistence, notifications, background work; exposes `:domain` as `api`) ← `:app` (`ui/` `MainActivity`, Compose screens + ViewModels, `widget/` Glance: one package per widget, `widget.order` / `widget.countdown`, with its composables in a `components` sub-package; the receivers, the shared config activity and `OrderRefKey` stay in `app.tostrr.widget`, because launchers bind placed widgets to the receiver's class name and moving it breaks them, `TostrrApp`). Clean-architecture rules: repositories are interfaces in `:domain` (`OrderRepository`, `ChecklistRepository`, `AuthRepository`, `OptionRepository`, `DeliveryCenterRepository`, `SyncScheduler`, `SyncSettingsRepository`, `NotificationSettingsRepository`, `AppearanceRepository`, `AccountRepository`, `UpdateRepository`), implemented in `:data` (`OrderRepositoryImpl`, `ChecklistRepositoryImpl`, `TeslaAuth`, `OptionCatalog`, `DeliveryCenterCatalog`, `RefreshScheduler`, `SyncSettingsRepositoryImpl`, `NotificationSettingsRepositoryImpl` (the `NotificationKind`s turned off in the settings' notifications section, one per channel, in the `tostrr_settings` shared preferences; `OrderNotifier` skips them, still recording reminders and digests as sent), `AppearanceRepositoryImpl` (the `ThemeMode`: like the phone, light or dark, in the `tostrr_settings` shared preferences; `MainViewModel` hands it to `TostrrTheme` and `applySystemBars`, the widgets to `widgetColors`, and `WidgetRefresher` redraws them when it changes), `AccountRepositoryImpl` (account name and picture from `GET /api/1/users/me`, refreshed best effort when the settings open; name and picture URL kept encrypted in `TokenStore`, the picture copied to `noBackupFilesDir`, all wiped on logout); Koin binds each to its interface). ViewModels, widgets and `TostrrApp` never touch repositories: they go through use cases in `app.tostrr.domain.<feature>.usecase` (`@Factory`, one action each, `operator fun invoke`), injected under names ending in `UseCase`. Exceptions shown to the user (`AuthException`, `SessionExpiredException`, `ApiException`) live in `app.tostrr.domain.error`. Each module is split into sub-packages by concern: `app.tostrr.domain.{order, history, alert, notification, checklist, deliverycenter, auth, sync, appearance, update, error, layout}` (`order` holds `Order`, `OrderMapper`, the step detectors and the delivery countdown; `history` holds `JsonDiff` and `HistoryIgnore`) and `app.tostrr.data.{api, auth, order, notification, sync, appearance, update, checklist, catalog, layout, di}`. Put new classes in the matching sub-package (tests mirror it). `:data` must not reference `:app`: notifications open the launcher intent and use the application icon rather than `MainActivity` / `R`.

**Sync pipeline** — the core flow, centred on `OrderRepositoryImpl.refresh()` (reached through `RefreshOrdersUseCase`):
1. `TeslaAuth` provides a valid access token (OAuth2 code + PKCE with Tesla's public `ownerapi` client; redirect `tesla://auth/callback` is caught by the manifest intent filter on `MainActivity`, or pasted manually). Tokens are encrypted with a Keystore key in `TokenStore`.
2. `TeslaApi` fetches `GET /api/1/users/orders` and, per order, the `/tasks` endpoint. Payloads are kept schema-less as `JsonObject`. While an order awaiting delivery has a VIN, the sync also reads the account's vehicles (`GET /api/1/products`, `TeslaApi.productVins`, best effort): the day an order's VIN first shows up there is kept as `LocalSignals.inAccountSince`, so `Order.delivered` (Tesla's `DELIVERED` status, or that day) holds even while Tesla's status lags; it closes the delivery step, takes the order out of `awaitingDelivery` and raises `Alert.Delivered`. That the car reaches the account only at the handover is a hypothesis, unchecked on a real delivery. An order whose `/tasks` fails keeps the details and `fetchedAtEpochMs` of its last sync while the others go on; the sync fails as a whole only when that order has no cached details or when every order fails.
3. `OrderMapper.map(order, details, fetchedAt)` builds the `Order` model, including the fixed list of `OrderStep`s. A VIN is only taken when the field holds 17 valid VIN characters (`OrderMapper.vinIn`): Tesla's placeholders (`VIN ##vin##`) don't count. Likewise an appointment only counts (step done, reminders, `Order.appointment`) when its text has a time of day; a bare day only becomes the cards' `deliverySlot`. Every field access is defensive and many dates are found by key name anywhere in the tree (`deepFind`) because Tesla moves fields around.
4. The raw JSON of old vs new is pruned by `HistoryIgnore` (paths, plus the Tesla staff handling the trade-in: `@tesla.com` e-mails and `employee` fields) and diffed by `JsonDiff`; deltas become `Change` entries in the per-order history. Tesla gives no date for the VIN, so `withVinAssignmentDate` (`domain/history`) dates its step from this history, on the way into the orders flow: the first sync that saw it; a VIN no entry dates (already there on the order's first sync) gets one at that sync, through `undatedVinChange`.
5. `OrderNotifier` (using rules in `OrderAlerts`) posts step-change, option-change, delivery-window, reminder, digest and sync-problem notifications.
6. State is persisted as JSON files in `filesDir` (`orders.json`, `history.json`) and exposed as `StateFlow`s; every pull is also archived as gzipped JSON in `getExternalFilesDir("snapshots")/<order>/` (pullable over adb for analysing real payloads).
7. Repositories expose state as flows, never listeners: `WidgetRefresher` (started in `TostrrApp`) collects the orders flow and runs `OrderWidget`/`CountdownWidget` `updateAll` on each new value (every sync emits one, as `fetchedAtEpochMs` changes).

Refreshes run from the UI (the refresh button, `OrdersViewModel`, and once right after login, `LoginViewModel`; never on app launch) and from `RefreshWorker` (periodic WorkManager job, scheduled by `RefreshScheduler` when logged in, every 15 min by default; in the settings screen, whose sections are items of one list, the user can turn it off (manual refresh only) or pick a `SyncInterval`, kept as `SyncSettings` by `SyncSettingsRepository` in the `tostrr_settings` shared preferences; `StartBackgroundSyncUseCase` then schedules with `ExistingPeriodicWorkPolicy.UPDATE` or cancels). A `Mutex` serialises them so diffs never see half-updated state. `AuthException`/`SessionExpiredException` mean "drop the session"; other failures retry.

**Unverified rules**: Tesla doesn't document how steps like "Production terminée", "Documents envoyés" or "Véhicule immatriculé" appear. `StepDetector` / `PayloadStepDetectors`, `HistoryIgnore` and parts of `OrderMapper` are guesses, not observed changes in real payloads. Treat them as hypotheses: when real snapshots with new values are available, check them against these rules before trusting either. Swap step logic through `StepDetectors` rather than editing `OrderMapper`.

**Crash reports**: Firebase Crashlytics (project `tostrr-977a4`, no Analytics), in `:app` only. `app/google-services.json` is git-ignored; the Google Services and Crashlytics plugins are applied only when it exists, so a clone (or CI without the secret) builds without it. Collection is on only in release builds that have it (`crashlyticsEnabled` manifest placeholder); R8 mappings are uploaded by the release build.

**Catalogues**: `PartsCatalog` asks Tesla's public parts catalogue (`epcapi.tesla.com/api/catalogs?vin=`, no token) whether it lists a VIN: it only lists cars that exist, so it marks the car built. At the start of each sync it looks up one VIN of the orders awaiting delivery (the one that waited longest, each at most hourly, never again once found; cache in `filesDir/parts_catalog.json`, wiped on logout); the day it was found reaches the order as `LocalSignals` (`domain/order`), kept in `Order.raw` under `local` so it is saved, diffed into the history and archived, and it marks and dates the built step on top of `StepDetectors.carBuilt`. The catalogue's `externalReference` comes along (`LocalSignals.partsCatalogReference`, `Order.partsCatalogReference`; a VIN found without one is looked up again): with the VIN it makes the link to the car's parts on parts.tesla.com (`Order.partsCatalogUrl`, in the device's `language-COUNTRY`), shown in the detail's vehicle block (`PartsCatalogRow`). `OptionCatalog` downloads option-code labels from tesla-order-status-tracker.de (best effort, cached, never fails a sync). `DeliveryCenterCatalog` reads the bundled `data/src/main/assets/delivery_centers.json`, a snapshot of tesla.com/findus; regenerate it with the project skill `refresh-delivery-centers` (`.claude/skills/`).

**Arranging the order detail** (ported from the sibling teslarr app): `domain/layout` has the blocks (`DetailBlock`, declaration order = default), the saved `BlockLayout(order, hidden, collapsed, shown)`, stored as changes from the defaults (a block can be `hiddenByDefault`, like the vertical progress; `shown` lists those the user turned on) (empty = default, never stored; "reset" only undoes order and visibility, collapsed sections stay collapsed) and the pure `BlockLayouts` functions (resolve with unknown ids dropped and new blocks slotted before their next default neighbour, move, toggle, toggleExpanded), used through `DetailLayoutRepository` and its use cases. `DetailLayoutRepositoryImpl` keeps it as JSON in the `tostrr_layouts` shared preferences. The detail top bar opens `detail/components/DetailLayoutSheet` (arrows and hide/show, applied at once, plus reset); the hero header stays fixed. A new block only needs an enum entry plus its title (`components/DetailBlockTitle.kt`), its label, blurb and icon (`components/BlockRow.kt`) and its branch in `DetailScreen`.

**Updates**: `UpdateRepositoryImpl` (`data/update`) reads the latest release from GitHub's public API, without token (drafts and pre-releases never come back), at most every 6 hours when the app comes to the foreground (`MainViewModel`), best effort, and compares its tag with the installed `versionName` (`AppVersions`); debug builds too, to see the screen, though Android refuses to install a release, signed with another key, over them. `MainActivity` opens `Screen.Update` once per version, only from the orders list. "Later" stops bringing that version up (kept in `tostrr_settings`), back only closes the screen until the next start; either way a section at the top of the settings leads back to it while it is newer than the installed one (`update` vs `updateToOffer`). The notes are the release's text, in the language it's written in, read by the small `ReleaseNotes` Markdown parser. "Update" downloads the asset to `cacheDir/updates` and opens the system installer through the `FileProvider` (`REQUEST_INSTALL_PACKAGES`); Android itself checks the signature, and asks the first time to allow installs from Tostrr.

**Checklist**: delivery-day checklist content is defined in `domain/checklist/DeliveryChecklist.kt`; answers and photos are stored per order in Room (`ChecklistDatabase`, version 1, no migrations yet — bumping the schema needs a migration) via `ChecklistRepository`, with photos under `filesDir/checklist_photos` shared through the `FileProvider`.

**ViewModels (MVI)**: one ViewModel per screen, from `ui/architecture/MVI.kt` (taken from the sibling KMP pigeonworkshop app; `watchAsState()` uses `collectAsStateWithLifecycle` here). A state that comes from flows extends `BaseViewModel` and defines `override val state` as a `combine` of the use-case flows, `stateIn(viewModelScope, WhileSubscribed(5_000), …)` (initial value from the `StateFlow`s' current values where the first frame matters), never by collecting flows in `init`; local state it keeps itself (e.g. the manual refresh in `OrdersViewModel`) is a private `MutableStateFlow` joined to the `combine`. `BaseViewModel2(State())` with `updateState` is only for a purely local state that depends on no flow (`LoginViewModel`). Each declares its nested `State` (data class with defaults), `Action` (named `On…`, handled in `onHandle`) and, when needed, `SideEffect` (one-off events: navigation, opening the camera or a browser tab), else `NoSideEffect`. The screen reads `viewModel.watchAsState()`, sends `viewModel.handle(Action…)` and reacts in `OnSideEffect(viewModel) { … }`; public screens take the ViewModel (`koinViewModel()`) and delegate to a private `…Content` composable where it keeps them simpler. `MainViewModel` only serves the activity (login state, order references for deep links, the update to offer); a Tesla redirect deep link is held by `MainActivity` and handed to `LoginScreen`.

**Navigation**: Navigation 3 (pinned to 1.1.x: 1.2 needs AGP 9.1). A single `MainActivity` owns the back stack (`rememberNavBackStack`) of `@Serializable` `Screen` keys (`ui/navigation/Screen.kt`: `Login`, `Orders`, `OrderDetail(reference)`, `Checklist(reference)`, `Settings`, `Update`) shown by a `NavDisplay`; each entry gets its own saved state and `ViewModelStore` through the entry decorators. Screen arguments come from the key, not the `SavedStateHandle`: `DetailViewModel` and `ChecklistViewModel` take the reference as a Koin `@InjectedParam` (`koinViewModel { parametersOf(reference) }`). Logging in or out replaces the whole stack. Widgets and launcher shortcuts use the internal deep links `tostrr://order/<reference>` (`MainActivity.orderUri`) and `tostrr://orders`. Shortcuts: a static "Commandes" one (`res/xml/shortcuts.xml`, whose `targetPackage` must match the applicationId) and up to three dynamic ones for the latest orders awaiting delivery, kept in sync with the orders flow by `shortcut/OrderShortcuts` (started in `TostrrApp`).

## Conventions

- Use only even `dp` values in Compose code.
- One composable per file, named after it (`OrderCard.kt`, `RememberBelowAnchorPositionProvider.kt`). Each screen's package (`ui/<screen>/`) holds only its public `…Screen` and its ViewModel; every other composable of that screen is `internal` in `ui/<screen>/components/` (the private `…Content` included). A constant or helper used by a single composable stays `private` in its file; one shared by several gets its own `internal` file in `components` (`TopBarHeight.kt`, `BreakablePath.kt`). Composables shared by several screens go to `ui/common` (`internal`), Glance ones to `widget/<widget>/components`. `ui/architecture/MVI.kt` is the one exception, kept as a single file.
- Don't commit unless explicitly asked.
- Don't `force-stop` the app on a device that has widgets/notifications set up: it resets widgets and cancels notifications.
